# CI/CD Basics

[Frontend CI](../../../.github/workflows/ci.yml) checks pushes to `main` and `dev`, including merges, all pull requests, and manual runs. Five jobs run in strict sequence through `needs` dependencies. Every job starts in a fresh Ubuntu workspace, recursively checks out the pinned shared contract, sets up Node.js 26 with npm caching, and runs `npm ci`. Repository permissions allow reads only; a newer run cancels an older run for the same workflow and ref.

| Stage and job ID | Checks and acceptance | Reports and artifacts |
|-----|-----------------------|---------|
| 1. Tests and coverage (`test`) | Run unit, component and contract tests with Vitest and collect coverage during test execution. Test failures or coverage below the configured thresholds fail the job. | Vitest JUnit and JSON, coverage HTML, LCOV and JSON summary. |
| 2. Type check (`checks`) | After Vitest and its coverage gates succeed, check application, configuration and test types. | Compiler diagnostics in the job log. |
| 3. Production build (`build`) | After type checking succeeds, validate the production bundle. | Upload `dist/` as `currency-quiz-build` after a successful build. |
| 4. Browser tests (`e2e`) | After the build succeeds, install Chromium and run Playwright against its own Vite frontend and fake API. Any failing case fails the job; retries are disabled. | Playwright HTML, JSON and JUnit, with traces and screenshots for failures. |
| 5. Mutation tests (`mutation`) | After browser tests succeed, run Stryker against question-form validation. A score below 75% fails the job; 85% is the improvement target. | Mutation HTML and JSON. |

Coverage gates require at least 80% aggregate lines, statements, functions and branches across the [selected source scope](../../../vitest.config.ts). Every metric must pass, but individual files do not each need 80% (`perFile: false`). This scope includes selected logic and `QuestionEditor`, rather than the whole application. Coverage is measured while tests execute and checked afterwards in the same run, so it cannot run as a standalone check before the tests. The [mutation configuration](../../../stryker.config.json) covers one module. These separate gates encourage checking relevant branches and assertions without treating a single high percentage as proof of correctness. TypeScript provides static checks; there is no separate lint stage.

A failure or skip prevents all later stages from running. Tests and their coverage gate come first, followed by type checking and bundle validation, before the more expensive browser and mutation suites. Browser tests use the existing isolated Vite server and fake API, not the uploaded production artifact. Parallelism remains inside test runners: Playwright uses two workers, fresh browser contexts and per-test API tenants so concurrent cases do not share records or session state. Vitest isolates files, restores mocks and uses fake clocks for timing boundaries. Role and label selectors, retrying browser assertions and explicit HTTP controls reduce timing dependence. Repeated failures should be diagnosed using the captured evidence; zero retries make a first failure visible rather than silently accepting a later pass.

The `test`, `e2e` and `mutation` jobs add step summaries and upload available reports even after a failing test step. These reporting steps use `always()` within the job; they do not allow downstream stages to run after failure. Reports and the successful build artifact are retained for 14 days. The stage-3 build artifact can remain available if a later browser or mutation stage fails; it does not establish that the whole pipeline passed. Open **Actions → Frontend CI → the failing stage**, inspect the first relevant diagnostic, then download its report. Type errors belong to `checks`, failed assertions and coverage to `test`, bundle failures to `build`, browser traces to `e2e`, and surviving mutants to `mutation`. Fix the cause and rerun the relevant local command before pushing.

Actions use explicit release tags: `actions/checkout@v7.0.1`, `actions/setup-node@v7.1.0` and `actions/upload-artifact@v7.0.2`. The [README](../../../README.md#continuous-integration) documents local commands for PowerShell 7+ and Linux/Bash. The [test strategy](../../testing-strategy.md) explains the environment, gates and evidence limits. The workflow builds the application without deploying it or changing Netlify settings. Configure branch rules to require all five named stage checks after the first hosted run; a workflow file alone does not enforce branch protection.

A hosted Actions run remains to be recorded after the changes are pushed. Step summaries and retained reports provide per-run visibility, but longitudinal coverage, mutation and failure trends need multiple saved runs. No historical flakiness baseline or demonstrated failed-run/fix/passing-run sequence is claimed. Browser tests use a fake provider; live-backend acceptance and provider verification of consumer expectations remain separate follow-up work.
